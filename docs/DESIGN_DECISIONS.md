# 设计决策与防守问答（面试 Q&A）

每个决策给出：结论、理由、证据位置。数字均来自 `backend/scripts/eval_report.md`（4000 笔防泄漏数据集，测试集 1200 笔）。

## 一、数据与评估

### Q1 为什么用合成数据而不是真实交易数据？

真实金融交易数据（如 IEEE-CIS）不可获取且含隐私，公开的 Kaggle 信用卡数据集特征维度与本系统的 6 类检测 Agent（5 规则：名单/交易/行为/设备/图关联 + 1 LLM 语义）不匹配。合成数据的优势是**带 ground truth 的受控实验**：能注入明确的冲突、边界、弱告警子人群，能做故障注入和逐模块消融——真实数据做不到这些受控实验。代价是数字不能直接外推到生产，这一点在 README 局限性中如实声明。生成器在 `backend/scripts/eval_common.py`，确定性（同 seed 全同，有测试保证）。

### Q2 标签泄漏具体怎么防的？旧数据集泄漏在哪？

旧 80 笔数据集：FRAUD 几乎只绑定 U9009/U2002/DEV-RISK-X/MCH-RISK-001 等特定身份，黑名单特征单独决定 8 笔标签，最优单 Agent 因此达到虚高的 F1 0.986。新数据集四层防线（`test/unit/test_eval_dataset.py` 逐项断言）：

1. **单特征 AUC 上限**：8 个单特征 AUC 全部 ≤0.82（陌生人 0.812、金额 0.804、黑名单 0.550），不存在单特征捷径；
2. **身份-标签独立性**：身份贪心均衡分配，user/merchant/device 与标签的偏离 ≤0.07/0.02/0.04；同一用户在两类中交叉出现（100% 用户双类出现）；
3. **分布重叠**：欺诈含 14.4% 小额试探（<2 万），正常含 4.5% 大额转账（>30 万）；
4. **黑名单覆盖仅 10% 欺诈**：一票否决路径只占真实少数，其余 90% 靠多信号融合。

风险类型身份（risk_x 设备、风险商户、黑名单）对标签有判别力，但那是**可观测特征**（device_risky/merchant_risky/blacklist_hit）携带的合法信号，ML 基线用派生特征而非原始 ID 即可获得同等信息——这不是泄漏。

### Q3 最优单 Agent F1 0.853 与集成 0.931 差距不算悬殊，集成的价值在哪？

三点，都有数据支撑：

1. **误报控制**：单 Agent graph-trace 精度 0.957 但召回只有 0.770（漏 138 笔欺诈）；集成同时拿到 0.904 精度和 0.960 召回。规则系统的延迟预算内不存在"事后知道哪个 Agent 最好"——单 Agent 的 0.853 是**用训练集先验选出来的**，如果信号分布漂移（图关联信号减弱），选错的代价无人兜底；
2. **故障容忍**（核心论据）：注入 1-2 个 Agent 降级后，集成 F1 仍 0.896、决策一致率 93.2%；任何单 Agent 方案在自身故障时直接失明。leave-one-out 消融显示去掉最强 Agent（graph-trace）集成只降到 0.885——集成没有单点依赖；
3. **可解释协作**：每个决策有 6 个 Agent 的独立意见（语义 Agent 不可用时回落到 5 规则）、冲突归因和仲裁理由，复核员能看到"谁在告警、谁反对、为什么这么裁"——单模型给不出这个。

### Q4 最优单 Agent 是怎么选的？为什么不在测试集上选？

在训练集（70%）上算 6 个 Agent 各自的阈值决策 F1，取最优（graph-trace；语义 Agent 在评估集无线索时保持降级剔除，不计入），再在测试集上报它的指标。如果直接在测试集上挑最好的 Agent，等于把选择信息泄漏进评估——测试集指标会偏乐观。这是评估方法论问题，监督基线同样遵守：所有 ML 模型只用训练集拟合。

### Q5 XGBoost F1 0.958 比规则系统 0.931 高，为什么不直接用 XGBoost？

诚实回答：在这份标注数据上监督模型确实更优（还有 2800 笔标注可训练的前提）。规则协同系统的定位不同：

1. **零训练样本冷启动**：规则+权重来自领域知识，不依赖标注数据；标注积累起来之后，系统通过复核反馈闭环在线学习权重（EWMA+收缩+softmax），这正是"数据飞轮"的起点；
2. **可解释与可审计**：金融风控要求每个 BLOCK/REVIEW 能给出证据链。规则协同天然给出逐 Agent 意见+冲突归因+仲裁理由；XGBoost 只能事后近似解释（SHAP）；
3. **故障容忍与优雅降级**：见 Q3；
4. **监督模型没有覆盖的路径**：孤立森林 0.576 证明无监督异常检测在此场景失效——"异常≠欺诈"，需要的是标注信号与规则知识的融合。

一句话：两者不互斥，监督模型分数可作为未来第 7 个 Agent 加入融合（与 LLM 语义 Agent 并列，都属于可插拔信号源）。

### Q6 孤立森林为什么只有 0.576？

欺诈在本数据集中不是"离群点"而是"模式组合"：小额试探在金额维度上与日常交易重叠，正常大额转账反而更像离群。孤立森林假设异常=稀疏区域，而欺诈密度不低。这个负面结果支撑了系统设计选择：需要多维度信号+标注反馈，而非无监督异常检测。

### Q7 规则系统的 AUC 0.983 怎么算的？和 F1 0.931 的差距说明什么？

AUC 用连续融合分（静态=算术加权分、多 Agent 协同=置信度加权融合分）对标签计算，分类器用 predict_proba。注意 AUC 口径**不含仲裁升级和一票否决**——这些是离散决策规则不是分数。0.983 vs 0.931 的差距恰恰说明：融合分的排序能力很好（AUC 高），但固定阈值切分（review 0.6/block 0.85）不是最优操作点——这是规则系统的已知代价（阈值全局固定 vs 监督模型按概率校准），也解释了为什么 XGBoost 的 F1 略高。

## 二、系统设计

### Q8 Agent 置信度是不是拍脑袋？消融显示"−置信度加权 ΔF1=0"，说明置信度没用？

置信度来自**特征覆盖度规则**（`agents.py`）：ListAgent 0.55+0.1×已核验字段数；BehaviorAgent 有画像+有地点 0.85、无画像 0.5；TransactionAgent 有交易对象 0.9、缺失 0.65……语义是"这个 Agent 本次评估看到了多少证据"。消融的诚实结果：在干净数据上把置信度恒置 1.0 决策不变（ΔF1=0），因为**召回由仲裁升级驱动、误报由选择性升级控制，融合分很少直接穿越阈值**。置信度加权的真实价值在异常路径：故障注入下剔除降级 Agent（其置信度 0.2 伴随 degraded 标记）、低置信离群降权 ×0.5 让弱告警融合分回落——消融表里"−仲裁层"（保留剔除与降权语义）F1 崩到 0.209，说明这一整层置信度驱动的仲裁机制是召回引擎。

### Q9 仲裁为什么只升不降（保守升级原则）？

风险不对称：漏放欺诈的资金损失 >> 误报转人工的运营成本。规则仲裁的升级条件全部是"存在可信风险主张"（高置信高分或硬证据），LLM 仲裁经合并层约束——规则侧 ESCALATE_REVIEW/BLOCK 不可被 LLM 降低（`collaboration.py::_merge_llm_verdict`）。反过来，降权只发生在**低置信离群意见**上（置信度 <0.6 且偏离中位数），且效果是让融合分自然回落放行，不是直接否决。这个设计让系统在"宁枉勿纵"和"误报爆炸"之间取得平衡：静态基线（冲突一律转人工）召回 0.993 但精度 0.763（600 误报）；多 Agent 协同精度 0.904 召回 0.960。

### Q10 降级 Agent 为什么剔除而不是注入保守分？

若把超时 Agent 按 0.8 分注入加权平均——问题：0.8 分接近 review 阈值，会把大量正常交易抬进复核区，故障注入下静态融合误报 600 笔、一致率仅 63.7%。多 Agent 协同改为剔除（置信度 0.2 + excluded_agents），剩余不足法定人数 3 个时保守转人工。故障注入结果：F1 0.896、一致率 93.2%、误报 44 笔。语义分析 Agent 同样走降级剔除：3.5s 超时/输出不可解析 → degraded 标记剔除，且不注入保守分、不参与冲突判定（analyze_conflict 只对有效 Agent 计算 spread/中位数）、不向学习闭环注入信号（record_feedback 跳过 degraded）。剔除的代价是信息变少，所以有法定人数下限兜底。

### Q11 EWMA、贝叶斯收缩、softmax 各解决什么问题？

（`strategy/learning.py`，反馈闭环）EWMA（α=0.3）：滚动准确率，近期复核结论权重更高，适应概念漂移；贝叶斯收缩（先验 0.7、K=10）：小样本时学习权重收缩回配置权重，防止 3 笔样本就"赢者通吃"地重排权重；softmax（T=0.3）：把准确率差映射为温和的权重比，避免极端权重。整个闭环有人工在环断点：学习权重只是建议，管理员对比查看（配置 vs 学习 + EWMA 演进曲线）后二次确认采纳才发布新策略版本（审计留痕）。

### Q12 LLM-as-Judge 的评估公平吗？生产 3s 预算超时怎么办？LLM 仲裁比规则好吗？

公平性设计：规则与 LLM 仲裁跑**同一子集同一输入**（同数据集 seed、同 Agent 输出、同冲突报告），对比的是最终决策对 ground truth 的指标；LLM 失败自动回退规则（与生产链路一致），回退率如实上报。生产预算问题：DeepSeek 推理模型实测仲裁延迟平均 8.9s（P99 15.8s），远超生产 3s 预算——评估采用**双预算法**：每案先按生产 3s 预算调用（测真实回退率），失败再以 15s 评估预算重试一次（测裁决质量），两个口径分开上报。

实测结果（120 案冲突子集，60 FRAUD/60 LEGIT）：生产 3s 预算内成功率 **0%**（全部超时回退规则仲裁，链路无损）；15s 预算下成功率 70%、决策一致率 75%；LLM 冲突子集 F1 **0.706 低于规则仲裁 0.825**（精度 0.545 vs 0.711，召回 1.000 vs 0.983）——LLM 过度保守（84 个成功裁决中 83 个要求升级），27 笔放行改复核仅 1 笔是欺诈。结论：在该基准上规则仲裁的"可信风险主张"选择性升级比 LLM 裁判更校准；LLM 的价值需要更好的 prompt 校准或非推理模型才能兑现——这正是如实上报负面结果的意义。生产含义：要么换非推理模型，要么接受高回退率（规则仲裁兜底），要么调预算换延迟。详见 `scripts/eval_llm_report.md`。

## 三、工程与局限

### Q14 为什么用 LangGraph 做图编排，而不是手写函数链或直接用普通函数调用？

显式图（StateGraph）解决的是"多 Agent + 条件路由 + 可观测 + 可回退"四个问题的组合，函数链只能解决前半个：

1. **条件路由成为一等公民**：检测图里 `analyze_conflict` 之后用 `add_conditional_edges` 按冲突状态路由到 arbitrate（仲裁）或 skip（直接融合），审核图里 retrieve 失败仍走 advise（规则模板兜底）——路由逻辑声明在图上，而不是散落在 if/else 里；
2. **状态对象可观测**：节点间传递的共享 State 就是决策轨迹（每轮意见、冲突报告、仲裁结果、降级列表），天然支持审计和前端"协同决策过程"时间线渲染；
3. **单点替换/回退**：图中任一节点异常（如 LLM 超时）可以原地降级（degraded 剔除、回退规则模板），主链路不中断——这是生产风控最看重的属性，函数链做异常回退要侵入调用方；
4. **可扩展**：新增 Agent 或决策步骤 = 加节点/加边，不动主流程（语义 Agent、审核助手都是后加进图的）。

代价是引入依赖（langgraph）和一层抽象，但换来的是"节点可观测 + 路由显式 + 失败可回退"的工程收益，对应 README 里"降级与回退成为图设计的一部分而非旁路"。

### Q15 RAG 案例库为什么用 TF-IDF（char_wb 2-3gram + 余弦）而不是向量数据库/embedding？

三条理由：

1. **中文免分词**：char_wb 的 2-3gram 直接在字符级切分，"哈尔滨/哈尔滨市/哈市"等变体天然命中；embedding 方案要先处理中文分词边界，且小语料下 embedding 的质量不稳定；
2. **规模匹配**：案例库是"复核沉淀"场景（seed 2 案 + 增量），量级是千级而非亿级——在千级语料上 TF-IDF 内存索引（余弦）延迟 <1ms，精度与 embedding 相当，但零外部依赖（不引入向量库/embedding API/GPU）；
3. **可解释与可复现**：TF-IDF 相似度可以直接输出"命中哪些词/权重"供审计；embedding 的相似度不可解释。README 局限里也声明：语料增长到十万级后应迁移 dense retrieval——这是规模驱动的技术债，不是选型错误。

### Q16 人工审核助手为什么单独成图？8s 预算怎么定的？LLM 失败怎么办？

审核助手是"人在环上"的决策支持，和实时检测链路（毫秒级、自动处置）是两个不同的 SLA 场景：

1. **为什么单独成图**：审核链路是 read_case → RAG retrieve → LLM advise 的串行编排，复用 LangGraph 的节点可观测与回退语义，但与检测图（并行 Agent + 冲突仲裁）拓扑不同，分开成图各自演进（`detection/graph_workflow.py` vs `review_assistant/graph.py`）；
2. **8s 预算来源**：DeepSeek 推理模型实测平均延迟 8.9s（README LLM-as-Judge 实测）。原 3s 预算实测成功率 0%（100% 超时回退模板），放宽到 8s 后实测约 2/3 命中（7414ms / 2630ms 成功，8412ms 超时回退）——审核是人工在环、非同步关键路径，多等几秒可接受，且超时自动回退规则模板，UI 明确标注"LLM 回退"徽章；
3. **降级与审计**：LLM 失败/超时/输出不可解析 → 回退规则基线（按风险分+冲突状态给 RELEASE/REVIEW_CONFIRM/ESCALATE），响应带 fallback 标记与 trace_id；建议永不直接落决策，必须人工"按建议处理"确认后才写复核结论（复核结论再回流为 RAG 案例与学习信号）——LLM 永远在人工监督环内。

### Q13 这个系统能上生产吗？有哪些已知局限？

能跑（docker-compose MySQL+Redis、sqlite 演示模式、LLM 可选、优雅降级、全链路审计），但作为演示项目有明确局限，如实声明：

1. **合成数据**：数字不可直接外推生产，真实数据上需重标定阈值与权重；
2. **规则可被规避**：金额分段、设备 X 后缀等规则一旦被黑产探知即可绕过——生产需要规则热更新（策略版本化已支持）与更多隐性特征；
3. **固定阈值**：全局 review/block 阈值不如概率校准（Q7）；
4. **单 LLM 提供商**：LLM 仲裁依赖外部服务，已通过超时回退+安全基线控制风险；
5. **欺诈 prevalence 50%** 是基准设定（统计功效），生产环境低 prevalence 下精度数字会显著变化，需要按真实先验重估。

承认局限本身就是评估可信度的一部分。
